# 复盘：批量正则编辑截断三个 Rust 文件

[English](2026-09-13-bulk-regex-corruption.md) | 中文

日期：2026-09-13 · 状态：已解决 · 严重度：低（无数据损失）

## 摘要

在一次大型多特性落地期间，一个用于跨 workspace 追加 struct 字段的 Python 批量脚本（正则加花括号配对）截断了三个 Rust 文件——`acp.rs`、`model_adapter.rs` 和 `session.rs`——各损失约 500–900 行。当次会话内即通过 `cargo check` 的解析错误与不合常理的 `git diff --stat` 行数变化发现；恢复来自 `git fsck --unreachable`，其中仍保留着当天的 `WIP on main` stash 快照。总返工约一小时；未损伤任何提交，也没有数据永久丢失。

## 时间线

1. 一个多特性变更正在进行中，`crates/operations/bootstrap/src/` 里有大量未提交编辑。
2. 为了给多个 struct 加同一个字段，一个 Python 脚本用正则匹配加花括号计数一次性编辑多个文件，而不是逐点精准编辑。
3. 脚本的花括号配对启发式错误跟踪字符串字面量与嵌套块，写入了截断的替换内容：`bootstrap/src/acp.rs`、`bootstrap/src/model_adapter.rs`、`bootstrap/src/session.rs` 各丢失 500–900 行。
4. 下一次 `cargo check` 报出了远离任何编辑点的解析错误——第一个硬信号。
5. `git diff --stat` 显示三个文件出现与"纯追加变更"不符的大幅负行数变化——确认是截断而非代码写错。
6. 立即停止编辑（不再向受损工作树写入）。
7. `git fsck --unreachable` 定位到当天 `WIP on main` stash 的悬空对象；三个文件受损前的内容都从该快照恢复。
8. 用逐点精准编辑重新应用特性改动；`cargo check` 与测试套件通过。

## 影响

- 约 1 小时返工，重新应用丢失的文件内容与在途的特性编辑。
- 无永久数据损失：未影响任何提交，stash 快照提供了完整恢复。
- 无用户可见影响：损坏内容从未编译或运行过。

## 根因

一次脚本化批量编辑对 Rust 源码施加了语法盲的变换（正则 + 花括号计数）。花括号计数看不到字符串、注释或宏，脚本对"struct 结束"的判断与解析器发生分歧，文件的整段尾部区域被覆盖。在一个本就很大的变更期间执行放大了爆炸半径——中间状态坏了，也要到下一次编译才容易被发现。

## 做得好的地方

- 验证纪律当场抓住它：`cargo check` 加 `git diff --stat` 审查在几分钟内把"奇怪的解析错误"变成"文件被截断"。
- 一有怀疑就停止编辑，而不是在损伤上叠更多改动。
- Git 的不可达对象存储保留了当天快照；知道去那里找（`git fsck --unreachable`）避免了手工重建文件。

## 行动项

1. **优先逐点精准编辑，而非脚本化批量编辑。** 正则/花括号配对脚本不得改写 Rust 源码；当变更横跨多处时，逐个修改或扩展受编译器检查的抽象。
2. **任何机械化多文件变更之后，运行 `cargo check` 并审查 `git diff --stat`。** 解析错误加不合常理的行数变化（尤其是纯追加变更出现的大段删除）是损坏的特征签名；两者单独出现都不足以定论。
3. **怀疑损坏时，先停止编辑并从不可达对象恢复，再做任何覆盖。** `git fsck --unreachable`（和 stash）保存着受损前状态；继续编辑恰恰会摧毁恢复所需的历史。
