2.2 安全亮点

① HTTP 客户端禁 redirect 防 Key 泄漏

// crates/llm/src/anthropic.rs:36-43
let http = reqwest::Client::builder()
    .connect_timeout(Duration::from_secs(10))
    .redirect(reqwest::redirect::Policy::none())  // 关键:防止重定向把 x-api-key 带去跨域目标
    .build()

配套有 anthropic.rs:398-461 redirect_is_not_followed_and_api_key_not_leaked 测试——双 TCP listener(A=301→B,B 接收)验证 key 永远到不了 B。这是教科书级的安全测试设计。

② Config 凭据 Debug 重写

// crates/config/src/lib.rs:38-50
.field("api_key", &self.api_key.as_ref().map(|_| "***"))

config/src/lib.rs:258-279 provider_config_debug_redacts_api_key 锁死真实 key 字符串永远不出现在 Debug 输出。AnthropicClient 故意不 derive Debug,避免整结构体 {:?} 时 key 意外泄露。

③ 终端消毒单点收敛

sanitize_terminal 是单点收敛,处理 CSI / OSC / C0 / C1 / DEL,fast path 在无控制字符时返回 Cow::Borrowed(零拷贝)。4 个 sink 全部走它:AgentMessageDelta、human_tool_begin、human_tool_error、Warning/Error。这意味着未受信任文本进入终端的所有路径都有审计点——M2 ratatui TUI 也可直接复用。

2.3 安全风险与缺口

P0 · M3 硬交付

Sandbox 缺位:Shell 工具当前执行任意模型命令,仅受超时、env 净化、cwd 锚定保护,无任何审批门。M1 阶段如果用户允许 agent 自主 shell,任何 rm -rf、curl | sh、chmod 777 / 都会被忠实执行。SPEC §17.5 已规划 M3 闭环。

P2 · 中等风险

EditFile 新字符串大小无上限(tools/src/fs_tools.rs:271-381):MAX_READ_BYTES=4MB 限制读取,但 replacen(old, new, 1) 不限制 new。模型可用 1 字节 old_string 替换成任意大文件 → DoS 风险。建议增加 MAX_EDIT_BYTES 校验。

P2 · 中等风险

Shell 不回收孙进程(tools/src/shell_tool.rs:5-9):kill_on_drop(true) 只杀直接子进程。Unix 上 setsid + 杀整个进程组;Windows 上用 Job Object。SPEC §17 M2 已识别。

P3 · 低风险

WAVECODE_SHELL 参数推测(shell_tool.rs:32-50):按可执行文件名是否含 cmd 决定参数风格。注释诚实地标注可能误判。低风险但建议加显式 WAVECODE_SHELL_STYLE env 变量。

4.3 单 actor + select! 模式详解

// crates/app-server/src/lib.rs:97-176
loop {
    tokio::select! {
        biased;  // 优先处理 pending FIFO,避免饿死已排队请求
        // ...pending drain...
        sub = submission_rx.recv() => {
            match sub.op {
                Op::UserInput { text } => {
                    // 二级 select!: turn vs 新 submission
                    tokio::select! {
                        result = session.run_turn(...) => { ... }
                        next = submission_rx.recv() => {
                            // Interrupt / Shutdown 优先处理
                        }
                    }
                }
                Op::Interrupt => { /* set flag */ }
                Op::Shutdown => { /* drain 2s then exit */ }
                _ => warn!("未实现的 op 变体,前向兼容忽略"),
            }
        }
    }
}

这是 Rust 异步编程的典范用法:biased 保证 pending 队列不被饿死;二级 select! 让用户能在 turn 中途发送 Interrupt/Shutdown;兜底 _ => warn! 让未来 Op 增删不破坏 M1 构建。

8.1 Rust 惯用法得分

12.1 项目总体评价

WaveCode M1 阶段产出的代码质量在 Rust AI agent 项目中属于上乘。架构纪律(SPEC §3 边界规则 + §4 协议约束 + §5.4 上下文组装顺序 + §17.5 演进路线)全部以代码 + 测试兑现,文档与实现完全对账。

最值得称道的几点:

  1. wire-format byte-level 锁定——协议契约的物理证据
  2. API key 全链路防护——Debug 重写 + 禁 redirect + 防泄漏回归测试
  3. #[non_exhaustive] + _ => warn!——协议层前向兼容的纪律化兑现
  4. 三 OS CI 矩阵——终端工具的最低门槛
  5. 8 个 stub crate 显式标注 YAGNI 理由——不假装实现、不留 TODO 噪声

12.3 不建议做的事

  • 不要为已存在的 7 个 crate 加 unused stub(如 memory crate 提前实现)——YAGNI 是 M1 的正确选择
  • 不要为 Session 强行拆文件——当前单文件高内聚优于过早模块化
  • 不要为应对 stub 引入 mock trait default impl——等真实落地后再决定 trait 形状
  • 不要提前引入 keyring crate 而不完成 auth 实现——半成品依赖是债务
